# 服务器自动化采集技术方案（草案）

> 状态：讨论稿 v2，待评审
> 方向：**先带外、暂缓 OS 侧**（评审定稿：第一步 Redfish）
> 背景：交换机已完成端口自动化采集（`services/portDiscovery/`，SSH/SNMP/Telnet → 解析 → diff 预览 → apply 落库）。本方案讨论服务器（物理机）的自动化采集如何复用该架构。

## 1. 采集目标与路径

服务器采集目标分两类：**硬件资产清单**（CPU/内存条/硬盘/电源/序列号）与**业务网口**（对齐现有 DevicePort 端口管理）。四条可选路径：

| 路径 | 采集目标 | 不依赖 OS | 前提条件 | 定位 |
|---|---|---|---|---|
| **Redfish**（BMC 带外） | 硬件清单 + 传感器 + 网卡，结构化 JSON | ✅ | BMC 网络可达 + 账号 | **第一步，主路径**，现代机型全覆盖 |
| **BMC SNMP**（BMC 带外） | FRU（序列号/型号）+ 传感器/健康 | ✅ | BMC 开 SNMP 服务 | **第二步**，老机型兜底（iDRAC6/7、iLO3/4 等 Redfish 支持不全的） |
| **OS 侧 SNMP**（带内） | 业务网口（IF-MIB，厂商无关） | ❌ | OS 装 snmpd，开 UDP 161 | 暂缓（技术结论已验证可行，见 §2） |
| **OS 侧 SSH**（带内） | 精确硬件清单（dmidecode/lsblk） | ❌ | Linux SSH 账号 | 暂缓（复用现有 SSH 驱动，随用随启） |

不采用：Agent 常驻（部署维护成本高，不做）；Windows 服务器带内采集需 WinRM，暂缓。

## 2. 关键结论（讨论共识）

1. **网口采集与硬件清单是两条线**：网口走现有 DevicePort diff + apply 流程；硬件清单进设备详情/动态字段，不塞端口表。
2. **BMC 带外采集不需要 OS**：Redfish 与 BMC SNMP 均走 BMC 管理口，机器关机可采；两者凭据可共用（BMC 地址 + 账号，SNMP 另需 community）。**带外是本方案优先方向。**
3. **BMC 上的 IF-MIB 只有 BMC 管理口自身**，采不到业务网口；业务网口将来若需带内采集，走 OS 侧 SNMP / SSH / Redfish。
4. **BMC SNMP 是 per-vendor 私有 MIB**（DELL-RAC-MIB、CPQHLTH-MIB 等），需按厂商写映射——与现有 `DRIVERS` 按厂商注册的结构一致。
5. **OS 侧 SNMP 技术上可行且近乎零新代码**（暂缓）：现有 `SnmpDriver` 只依赖 IF-MIB（MIB-2 标准，服务器 snmpd 同样实现），仅需补虚拟接口过滤（`lo`/`docker0`/`veth`/`tun`，按 ifType=ethernetCsmacd 过滤）；且"免登录"是错觉——需逐台装配 snmpd。此结论保留，供后续阶段直接启用。

## 3. 架构接入方式

复用现有 portDiscovery 架构（凭据 → 驱动 → 解析 → diff → apply），新增最小改动：

- `DeviceCredential.protocol` 增加 `redfish`；BMC 地址复用 IP 字段或新增 `bmcAddress`
- 新建 `services/serverDiscovery/`，驱动按协议/厂商分：`redfish.js`（协议级，第一步）、`bmcSnmp/<vendor>.js`（老机型，第二步按需）
- 采集结果分流：
  - 硬件清单 → 更新设备详情 / 动态字段（落库目标待评审确认）
  - 网卡端口 → 走现有 DevicePort diff + apply（Redfish 可获取网卡信息，带外即可覆盖）
- 厂商识别：Redfish `Manufacturer` 字段直出，无需探测

## 4. 实施路线

| 阶段 | 内容 | 说明 |
|---|---|---|
| 第一步 | Redfish 采硬件清单 + 网卡 | 主路径：结构化 JSON 无需解析器，覆盖现代机型；需确认 BMC 网络可达 |
| 第二步 | BMC SNMP 补老机型 | 按实际老机型品牌按需开发 per-vendor 驱动（iDRAC6/7、iLO3/4 等） |
| 暂缓 | OS 侧 SNMP / SSH 带内采集 | 技术结论已验证（§2），需要时随时启用，无返工成本 |
